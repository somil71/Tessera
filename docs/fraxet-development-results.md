# FraXet exposed-model development result

Recorded 2026-11-24 **after** the [frozen FraXet holdout failed preflight](fraxet-holdout-result.md). These runs improve supported model coverage but cannot repair that held-out failure or count as an unseen pass.

The externally authored [FraXet RGB U-Net](https://huggingface.co/ayoubft/fraXteX) has 53 ONNX nodes, including two `Div` nodes for in-graph RGB preparation. The local graph analyzer already handled `Sub`; adding spatially uniform `Div` to its pointwise set and adding ONNX broadcast shape inference for `Div` in the Rust graph splitter made the model schedulable. Analysis derives a 112-pixel halo and 16-pixel alignment. The model is pinned at SHA-256 `b50e3c714a0447fae3da175c999c239b503cb98c0c3363e8d790f7c0fd7948fe`.

On the reserved synthetic RGB development inputs, the fixed 64² run matched the unsplit ONNX Runtime reference exactly. A four-tile fixed 128² run also matched exactly. On the 512² input, a **four-tile** fixed schedule with tile size 256, cut 0, two threads, and in-memory boundary storage matched all 262,144 FP32 probabilities exactly, including tile boundaries. Its raw Windows Job Object peak was 900,005,888 bytes under the enforced 1,073,741,824-byte limit; sampled private commitment peaked at 899,940,352 bytes; execution took 4.65 seconds. CRS EPSG:32643 and the input transform were preserved. A one-tile fixed 512² run also matched exactly and peaked at 924,532,736 bytes.

The automatic 512² run chose tile 512, cut 0, in-memory storage, and matched the unsplit reference exactly in 11.62 seconds including 8.88 seconds of planning. Its raw `PeakJobMemoryUsed` counter was 1,873,657,856 bytes despite no recorded failed candidate, while sampled private commitment peaked at 926,224,384 bytes. Per [amendment 2](evaluation-amendment-2.md), the automatic memory evidence is **inconclusive** when the raw counter exceeds the cap without a recorded failure. The isolated fixed runs show the selected schedule can execute under the cap, but they do not explain or waive the automatic counter. The planner's probe and execution accounting need isolation or further Windows Job Object investigation before claiming the strict memory criterion.

A later scheduler change gave every complete-raster attempt a nested hard-capped Job Object while retaining the outer planning job. On the same 512² exposed input, automatic output remained exactly equal to the oracle; the **selected execution job** peaked at 927,129,600 bytes under 1 GiB, while the **outer planning-and-execution job** retained its anomalous 1,873,219,584-byte raw peak. This separates the execution measurement but does not retrospectively turn the failed holdout into a pass or resolve the outer counter under the frozen evaluation rule.

This model is used only as exposed development material. A fresh independent model and a frozen manual candidate list remain necessary for a protocol pass.
