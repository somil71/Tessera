# Windows runtime resource accounting

The scheduler and its Rust children join one memory-limited Windows Job Object. The configured hard limit is the enforcement mechanism. Reports retain the raw `job_peak_committed_bytes` counter and a conservative value that adds scheduler commitment from before assignment. After rejected planner probes, the raw counter has been observed above the configured limit even when the selected run completes. [Evaluation amendment 2](evaluation-amendment-2.md) defines how to audit that case without hiding the counter value.

An exposed FraXet development run showed a second ambiguity without a failed candidate. In a 1 GiB job, the raw job peak after one successful warmup and three successful inferences in the **same worker** was 797,298,688, 1,334,173,696, 1,872,130,048, and 1,872,130,048 bytes. The worker's reported `PeakPagefileUsage` followed the same progression. A repeat diagnostic recorded the worker's **current** private commitment as 735,154,176 bytes after each inference, while its reported process peak rose to 1,809,997,824 bytes and the job peak to 1,873,276,928 bytes. The 50 ms sampled sum of live private commitment peaked at 926,072,832 bytes in the first run. A separate fixed one-inference run of the selected schedule peaked at 924,532,736 bytes and matched all scores. The automatic report now retains `probe_process_current_commit_sequence_bytes`, `probe_process_peak_sequence_bytes`, `probe_job_peak_sequence_bytes`, the raw counter before and after full execution, and active process counts at that boundary so this pattern can be investigated rather than obscured. In the repeat diagnostic, the inflated raw peak was already present **before** full execution, with only the scheduler process active.

Microsoft documents that [`JOB_OBJECT_LIMIT_JOB_MEMORY`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_limit_information) rejects a commit that would exceed the job-wide limit and describes [`PeakJobMemoryUsed`](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_extended_limit_information) as the peak of job processes. The documentation does not explain this observed divergence. The repeated-inference cause is an inference from the measurements, not a documented counter contract. A raw peak above the cap without a recorded failed probe remains **inconclusive** under amendment 2, even when the selected fixed schedule passes separately. The planner needs phase-isolated resource accounting or a verified explanation before a final memory pass claim.

Current reports also include:

- `job_peak_working_set_sampled_bytes`: the largest observed sum of live job-process working sets, sampled every 50 ms and once at report generation. `working_set_sample_count` and `working_set_incomplete_samples` describe coverage. This is **not an exact peak**; short spikes can be missed.
- `job_peak_private_commit_sampled_bytes`: the largest observed sum of live job-process `PrivateUsage` values at those same samples. This is a current private-commit measurement, not an atomic or exact historical job peak. `job_enforced_limit_bytes` records the configured hard limit. `job_peak_counter_exceeds_budget` compares the raw job peak with that limit; `job_peak_conservative_exceeds_budget` compares the raw peak plus pre-assignment scheduler commitment with the requested budget.
- `job_io_read_transfer_bytes`, `job_io_write_transfer_bytes`, and `job_io_other_transfer_bytes`: cumulative Windows Job Object I/O transfer counters. They include processes that have exited. These are **not physical disk-only bytes**; model loads, raster I/O, pipes, and other I/O may contribute.
- The attention path separately reports the sizes of its disk-backed staging arrays and output. Other schedules still need a peak temporary-storage measurement.

These meanings follow Microsoft's [Job Object accounting](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_and_io_accounting_information), [I/O counters](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-io_counters), [process ID list](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_process_id_list), and [process memory counters](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-getprocessmemoryinfo). The remaining v1 measurement gap is a defensible disk-only traffic estimate and exact or explicitly bounded working-set peak.
