# Public remote-sensing model compatibility probe

Recorded 2026-11-23. This is a development compatibility probe, not the independent holdout or a map-quality test.

The external [FieldsoftheWorld FTW-Q model](https://huggingface.co/fieldsoftheworld/ftw-q) is an agricultural-field boundary U-Net with an ONNX FP32 export, dynamic spatial dimensions constrained to multiples of 32, 16 input bands, and three output logits. Its model card specifies Sentinel-2 quarterly mosaics and preprocessing. We pinned Hugging Face revision `fc182b29879d5bcf20dc4e28cb758731817fbf3f`; the downloaded `ftw-q-unet-efb3.onnx` was 51,037,786 bytes with SHA-256 `d14285f91870a79833aac3529650f385afec605ed415acdf2227a02a0a88d036`. The downloaded file is ignored under `models/public/`.

The graph has 439 nodes. Its operator inventory includes Conv, Sigmoid, Mul, ReduceMean, Add, Shape, Concat, Relu, Resize, and BatchNormalization. The first preflight rejected node 5, BatchNormalization. After adding pointwise operators, it rejected node 391, Concat. After adding a general local graph path with channel-axis Concat, `scripts/doctor.py` rejected a 16-band 32×32 synthetic compatibility raster before inference at **node 393, Resize**. The model still does not match a validated raster schedule. The synthetic raster did not use the model card's reflectance preprocessing and was not used to assess prediction quality.

The probe demonstrates a concrete support gap: useful external segmentation models can contain common operators and topology beyond the frozen engineering fixtures. Its 26 `ReduceMean` nodes use initializer axes `[-1, -2]`, reducing across both spatial axes. Those intermediate global dependencies mean that accepting its nearest-neighbor Resize nodes alone would not make independent local tiles exact. Supporting this model requires a cross-image execution schedule for its repeated reductions, validated Resize semantics, numerical comparisons, and memory planning for the full graph. The model is now exposed to development and is ineligible as an unseen holdout.

## HydroFlow development probe

On 2026-11-24, we downloaded the external [HydroFlow water segmentation model](https://huggingface.co/egyx/hydroflow-water-segmentation) at Hugging Face revision `47c399ee0cf612759d3ad664239705dddfb7b85b`. The 97,860,996-byte FP32 ONNX file has SHA-256 `22a283eecd573b2700817a018dbbbb17871e8dfaedf55e9f8f0a779924338b94`. Its 206-node graph has one dynamic NCHW FP32 input with 12 bands and one dynamic one-band FP32 output. The upstream repository also supplies a 128×128, 12-band sample TIFF (SHA-256 `fa4613686e567dbf0434cc4f1a8b9d81bfd2712f03a8ac0b9c4a68dae8ed3f71`), but that sample has **no CRS or geotransform**. It is not suitable as a georeferenced product trial.

`scripts/doctor.py --model models/public/hydroflow-best-model.onnx --input data/public/hydroflow-sample-1-lake.tif --memory-limit-mib 2048` rejected the pair before inference. Its report retained both reasons: the source lacks a CRS, and the first unsupported graph node is 87 (`Constant`). The graph also includes `Shape`, `Gather`, `Unsqueeze`, `Slice`, `Cast`, and five `Resize` nodes used by the decoder. The author's preprocessing requires per-band min/max clipping and normalization, which the current scalar scale/offset CLI does not express. This is a measured compatibility result, not an execution or map-quality result. Both model and sample are now exposed development material and cannot serve as a new unseen holdout.

The preflight now records model/input hashes, tensor names/shapes/types, an operator inventory, and raster metadata even when family validation fails. That makes unsupported real models diagnosable without claiming that an operator inventory alone proves a valid execution schedule.
